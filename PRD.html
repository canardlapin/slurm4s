01 · Executive summary

A low-level Slurm library built around truth, not happy paths

slurm4s will provide Scala 3 applications with a composable interface to Slurm on the HPC system itself and from remote clients over SSH. It will expose Slurm's scheduling primitives without collapsing the different meanings of command invocation, scheduler acceptance, queue state, workload execution, logs, and typed results.

The library has two related surfaces:

  1. A raw typed scheduler interface for submission, observation, accounting, cancellation, capabilities, and logs.
  2. An optional managed controller for durable intent, idempotency, ambiguous submission recovery, coalesced observation, cursors, and restart-safe event delivery.

Opaque Python, R, shell, and other scripts are first-class. They may expose only exit status and logs, or opt into declared outputs and a language-neutral structured result protocol. Typed Scala computations use registered, versioned operations with encoded inputs and outputs; arbitrary closures or IO[A] values are never serialized.

Core proposition. Robustness comes from explicit uncertainty, durable evidence, bounded effects, and recoverable protocols—not from pretending Slurm is a synchronous function call and not from binding directly to libslurm.
02 · Problem

Driving Slurm is a distributed diagnosis problem

A conventional wrapper treats a batch submission as a subprocess returning a job identifier. Real usage presents a wider and messier state space:

Before acceptance

  • SSH, authentication, host-key, and network failures
  • missing Slurm commands or incompatible output formats
  • invalid account, partition, QoS, topology, or memory request
  • local validation succeeding while a site plugin still rejects the job
  • controller acceptance followed by a lost response

After acceptance

  • long or indefinite queueing with changing reasons
  • preemption, requeue, suspension, timeout, OOM, or node failure
  • successful scheduler completion but invalid application output
  • nonzero program exit, missing executable, missing file, or script error
  • delayed accounting and temporarily missing or buffered logs

These conditions must not be flattened into one exception or one linear Pending → Running → Done enum. A user needs to know what is confirmed, what is suspected, what evidence supports it, and which observations may be stale.

Why existing approaches are insufficient

  • Shell wrappers are easy to start but tend to use fragile text parsing, unbounded polling, implicit environment inheritance, and ambiguous retry.
  • Synchronous job APIs conflate scheduler acceptance with terminal completion and tie remote lifetime to a caller fiber or SSH channel.
  • Exception-heavy APIs make ordinary remote unavailability indistinguishable from defects and lose partial evidence.
  • Native bindings add JNI/JNA, native lifecycle, packaging, and major-version coupling without solving distributed ambiguity.
  • Generic workflow engines solve a different problem and often obscure the exact Slurm evidence needed for diagnosis.
03 · Vision and principles

Make uncertainty a value

Make Slurm interaction a typed, effectful, evidence-preserving boundary that stays honest when the environment is incomplete, asynchronous, and partially unavailable.

Truthful

Unknown, stale, unavailable, rejected, and failed are different states. The library never invents a terminal result from missing evidence.

Functional

Pure normalization and reducers surround explicit effects. Resource ownership, cancellation, time, and concurrency remain visible.

Layered

Scheduler semantics, transport, durable control, workload meaning, result decoding, and high-level orchestration remain separable.

Design principles

  1. Expected mess is domain data. Routine transport, scheduler, parsing, accounting, and workload failures are values, not unstructured exceptions.
  2. Persist before publishing. Live FS2 streams accelerate delivery; durable state and cursors survive process loss.
  3. Remote jobs outlive local resources. Closing a process, SSH channel, stream, or fiber never implies scancel.
  4. Interpret effects at the edge. Domain values are ordinary immutable Scala data; deployable programs choose IO.
  5. Preserve evidence. Known fields are normalized while bounded raw responses and unknown values remain available.
  6. Prefer explicit protocols over inference. Structured worker receipts are authoritative; log recognizers provide conservative hints.
  7. Use the lowest sufficient integration. Standard Slurm commands are the baseline; REST and native bindings must earn their cost.
  8. Types encode stable invariants, not transient certainty. Runtime observations remain ADTs because remote facts can become stale immediately.
04 · Users and jobs

Primary users

Scala library author

Needs a low-level, testable Slurm boundary beneath a scientific application, workflow tool, service, or desktop client.

HPC application developer

Needs local and remote parity, structured diagnostics, explicit resources, and site-aware behavior without becoming a Slurm parsing expert.

Scientific tool author

Submits opaque R or Python scripts today and may later adopt declared outputs, structured progress, or typed task results.

Operations-minded maintainer

Needs bounded controller traffic, restart-safe state, raw evidence, version discovery, and a deterministic failure simulator.

Core jobs to be done

  • Submit a job locally on an HPC login node and receive an unambiguous typed submission outcome.
  • Submit the same job through an existing SSH configuration without changing its scheduler semantics.
  • Reconnect after the desktop, network, SSH session, or agent disappears and recover the current job evidence.
  • Understand whether a job is waiting, rejected, running, requeued, preempted, out of memory, or failed inside the workload.
  • Resume stdout and stderr from exact byte cursors and retain useful bounded tails in a failure report.
  • Run an opaque script without forcing it into a bespoke worker protocol.
  • Run a registered typed Scala operation and recover a typed return value or structured failure.
  • Build higher-level workflow, retry, artifact, or user-interface behavior without bypassing the low-level evidence.
05 · Goals and non-goals

Product boundaries

Goals

  • Local and OpenSSH-mediated remote Slurm access
  • Typed requests, observations, failures, receipts, and cursors
  • Effect-polymorphic services with Cats Effect IO at assembly
  • Opaque scripts, declared outputs, structured results, and typed Scala tasks
  • Resumable bounded logs and evidence-based diagnosis
  • Durable optional control plane with idempotent submission
  • Capability negotiation across heterogeneous Slurm sites
  • Deterministic model and fault-injection testing

Non-goals

  • A DAG or scientific workflow engine
  • A general distributed collection or data-processing framework
  • Exactly-once physical scheduler execution
  • Serialization of Scala closures, IO[A], or JVM object graphs
  • Automatic proof that arbitrary side effects are retry-safe
  • A sandbox for user-supplied scripts
  • A Slurm administrator or cluster-policy management API
  • A promise that every site exposes live logs or accounting
  • Inferring authoritative failures from regexes over arbitrary log text
  • Requiring slurmrestd or native libslurm
Trust boundary. An opaque script is user-supplied code running with that user's Unix and Slurm authority. slurm4s will avoid introducing additional command-injection paths, but it is not a workload sandbox.

Effect model

  • Reusable algebras are parameterized by F[_] and ask for the weakest useful Cats Effect capability.
  • Deployable client and agent programs use IO.
  • Resource scopes local processes, SSH channels, handles, and files—never remote job lifetime.
  • Temporal owns bounded backoff, jitter, polling, and timeouts.
  • FS2 owns bounded live movement of bytes, log chunks, protocol frames, and committed events.
  • Domain state and persisted messages contain no Cats Effect or FS2 runtime types.

Public algebra sketch

trait Scheduler[F[_]]:
  def capabilities: F[SchedulerCapabilities]
  def submit(spec: ResolvedJobSpec): F[Submission]
  def observe(jobs: NonEmptyVector[JobRef]): F[ObservationBatch]
  def accounting(jobs: NonEmptyVector[JobRef]): F[AccountingBatch]
  def cancel(job: JobRef): F[CancellationResult]

trait SlurmExecutor[F[_]]:
  def submit[A](payload: Payload[A], resources: ResourceRequest):
    F[SubmittedJob[A]]
  def snapshot(job: DurableJobHandle): F[ManagedObservation]
  def await[A](job: SubmittedJob[A]): F[ExecutionResult[A]]
  def events(job: DurableJobHandle, after: EventCursor):
    Stream[F, JobEvent]
  def logs(job: DurableJobHandle, from: LogCursor):
    Stream[F, LogEvent]
  def cancel(job: DurableJobHandle): F[CancellationAcknowledgement]

Routine remote failures are returned in these ADTs. Failure of F is reserved for caller cancellation, defects, and failures that the interpreter cannot safely classify.

Opaque scripts

The library accepts inline content, a local file to stage, or an explicitly remote source. Script bytes and relevant launch inputs receive a canonical digest. Exit-only success claims no more than scheduler/process evidence supports.

A script may declare expected relative outputs without adopting the full worker protocol. Missing outputs then become a distinct result-validation failure even when the process exits zero.

Language-neutral result envelope

A protocol-aware workload writes one bounded result envelope atomically and last. The envelope binds protocol version, submission, attempt epoch, operation, result schema, status, value, declared outputs, sizes, and digests. Python and R helpers should be possible without making them core runtime dependencies.

Registered Scala computation

trait ScalaTask[I, O]:
  def id: OperationId
  def version: OperationVersion
  def inputSchema: SchemaId
  def outputSchema: SchemaId
  def run(input: I, context: TaskContext[IO]): IO[O]
  • The submitted value contains an operation reference and encoded input, not a serialized function.
  • The implementation is delivered as a versioned worker distribution, assembly, or container with a content digest.
  • The worker registry resolves operation ID and version before execution.
  • Large values become staged outputs; the returned typed value remains bounded control data.
  • Task code may use effect-polymorphic internal components, while the deployed worker selects IO.

File I/O and task context

trait TaskContext[F[_]]:
  def inputs: InputAccess[F]
  def outputs: OutputStaging[F]
  def scratch: Resource[F, ScratchDirectory]
  def progress(event: ProgressEvent): F[Unit]
  def logger: TaskLogger[F]

A managed task uses logical input and output names rather than serialized client-local paths. A lower-level native context may expose more direct filesystem access, but it must not be presented as capability isolation or retry safety.

Typed reconnection

The durable handle stores ResultSchemaId, not a Scala type parameter. Reattachment requires a compatible ResultContract[A]; a schema mismatch is detected before reading result bytes.

Typing does not prove idempotence. A typed task may update a database, send mail, or mutate a shared file. Retry safety is a separate declared policy and defaults to unknown or no automatic retry.
10 · Local and remote execution

Same scheduler semantics, different command locality

Local mode

When running on an HPC login or service node, the CLI interpreter launches fixed Slurm executables through fs2.io.process. Commands use argument vectors, a controlled working directory, a sanitized environment, concurrent stdout/stderr draining, explicit timeouts, and bounded capture.

Remote mode

The client uses the site's configured system OpenSSH executable and normal host aliases, host-key policy, agent, proxy, and MFA behavior. It starts or attaches to a fixed remote command:

ssh <configured-options> <host> slurm4s-agent serve --stdio

The client and agent exchange framed, versioned messages. The remote command remains constant; user values are protocol data rather than interpolated shell fragments. The agent invokes Slurm commands locally on the cluster and owns only user-level state.

Agent lifecycle

  • The initial agent may be an on-demand process attached through stdio.
  • The managed mode persists intent and journal data in a permission-restricted user directory.
  • Agent restart reopens state and reconciles nonterminal attempts.
  • A site may supervise a persistent agent, but no inbound port is required by default.
  • Agent distribution installation, digest verification, and atomic adoption are explicit later capabilities.

Direct SSH compatibility mode

A constrained direct-command adapter may be offered for bootstrapping, but it is not the correctness-defining remote path. It must advertise reduced capabilities, especially around quoting, durable control, paged logs, and recovery.

11 · Slurm integration

CLI first, REST optional, native only with evidence

Baseline command set

  • sbatch --parsable for submission and job binding
  • squeue --json=<data-parser> for active observation
  • sacct --json=<data-parser> or explicit --parsable2 fields for accounting
  • scontrol --json=<data-parser> show job for focused reconciliation and diagnostics where supported
  • scancel for explicit asynchronous cancellation requests

Compatibility discipline

  • Discover Slurm version, cluster identity, command availability, accounting availability, and supported data-parser versions.
  • Request a known JSON data-parser version instead of silently depending on the latest default.
  • Keep version-scoped DTOs and codecs inside the interpreter.
  • Use explicit fallback field sets and strict parsers where JSON is unavailable.
  • Preserve unknown states, flags, reasons, fields, warnings, and bounded raw responses.
  • Treat parse failure as an observation failure with evidence, never as job failure.

Controller load

One coalescing observation service operates per site. It batches job references, rate-limits calls, uses jittered adaptive cadence, moves terminal candidates from squeue to sacct, and reserves focused scontrol probes for ambiguity. There is no one-polling-loop-per-job design.

12 · Durability and recovery

Acceptance is asynchronous and may be ambiguous

IntentRecorded→ SubmissionPending→ Submitting→ Bound→ Pending / Running / Requeued→ Terminal

AcceptanceUnknown branches from Submitting whenever Slurm may have accepted the request but the client or agent cannot prove the returned binding.

Submission protocol

  1. Normalize the request and calculate a canonical digest.
  2. Persist SubmissionKey, digest, intent, and accepted-at time.
  3. Append the intent event before scheduler action.
  4. Claim a submission epoch and persist Submitting.
  5. Invoke sbatch once for that claimed epoch.
  6. Capture stdout, stderr, exit, timing, parse result, and command capability version.
  7. Persist the scheduler binding, or record AcceptanceUnknown.
  8. Reconcile uncertain acceptance using site-supported correlation metadata and active/accounting evidence.

Idempotency and fencing

  • The same submission key and digest returns the existing intent or receipt.
  • The same key with different content is a conflict before scheduler action.
  • Blind automatic resubmission is forbidden while acceptance is uncertain.
  • Attempt epochs fence structured results and staged outputs from stale duplicate workers.
  • Exactly-once scheduler execution is explicitly not promised.

Observation semantics

Every observation includes source, observation time, last successful contact, and freshness. Empty query, timeout, authentication failure, parser failure, unavailable accounting, and confirmed not-found remain different outcomes. Requeue and flags are retained as history rather than forced into a false monotonic scheduler sequence.

Cancellation

Cancellation is an idempotent requested/acknowledged/reconciled protocol. Closing a stream or canceling a caller fiber never invokes scancel. A race between completion and cancellation produces one evidence-backed reconciled terminal outcome.

13 · Logs and diagnosis

Resumable bytes, conservative interpretation

Submission-time layout

attempts/<submission-key>/
  stdout-%j-r%r.log
  stderr-%j-r%r.log
  worker-events.ndjson
  worker-result.json

Array paths include %A and %a. stdout and stderr are separate by default. Open mode is explicit rather than inherited from site configuration. Attempt directories are private and created before submission.

Cursor model

final case class LogCursor(
    stream: LogStream,
    generation: LogGeneration,
    offset: Long
)

enum LogEvent:
  case Chunk(from: LogCursor, next: LogCursor, bytes: Chunk[Byte])
  case WaitingForFile(stream: LogStream)
  case GenerationChanged(previous: LogCursor, next: LogCursor)
  case Truncated(previous: LogCursor, next: LogCursor)
  case Gap(stream: LogStream, reason: Diagnostic)
  case TemporarilyUnavailable(lastKnown: LogCursor, reason: Diagnostic)
  case End(stream: LogStream, finalCursor: LogCursor)
  • Bounded page reads are fundamental; follow is derived as an FS2 stream.
  • Bytes are authoritative. Text and line decoding are optional incremental views.
  • Missing files while pending produce WaitingForFile, not failure.
  • Generation, size, and file identity detect restart, replacement, and truncation.
  • Terminal jobs receive a bounded final-drain grace period for delayed filesystem visibility.
  • A slow log consumer cannot block scheduler reconciliation.
  • If login and compute nodes do not share the relevant filesystem, the site reports live logs unavailable and may support completion-time retrieval only.

Diagnosis

enum Assessment[+A]:
  case Confirmed(value: A, evidence: NonEmptyChain[Evidence])
  case Suspected(candidates: NonEmptyChain[Candidate[A]])
  case Undetermined(evidence: Chain[Evidence])

Scheduler state, reason, flags, exit and signal, accounting, worker receipt, structured progress, stdout/stderr tails, and result validation contribute to one diagnosis. Built-in log recognizers may identify common tracebacks or runtime messages, but they return suspected causes with byte-range evidence. They never override stronger scheduler or worker evidence.

Structured worker events

The optional worker launcher appends versioned events such as worker started, process started, progress, process exited, and result written. It distinguishes inability to execute a program from a program that started and failed. Loss by OOM or node failure may prevent the final receipt; absence therefore remains evidence, not a complete diagnosis.

Privacy and retention

  • Log pages, lines, and diagnostic tails have explicit size limits.
  • Raw workload logs are not copied into operational telemetry by default.
  • Rendering/redaction is separate from raw evidence so stored bytes are not silently altered.
  • Retention and cleanup policy is explicit and reports gaps after deletion.
14 · Resources and site policy

Portable intent, site-specific resolution

final case class JobSpec(
    launch: LaunchSpec,
    resources: ResourceRequest,
    environment: EnvironmentSpec,
    metadata: JobMetadata
)

enum MemoryRequest:
  case PerNode(bytes: PositiveBytes)
  case PerCpu(bytes: PositiveBytes)
  case AllNodeMemory

Resource types should prevent simple contradictions and retain Slurm's meaningful alternatives. Pure validation accumulates errors. Site-aware preflight resolves portable intent through a SiteProfile into partition, account, QoS, constraints, memory convention, modules, containers, accelerators, limits, and native options.

Rules

  • Record both requested and effective resource specifications.
  • Preflight is advisory; live controller policy and submission plugins remain authoritative.
  • Unknown native capabilities and reasons survive normalization.
  • Advanced Slurm-native options are isolated from the portable API and never become shell text.
  • Environment export policy is explicit; accidental inheritance is not the default contract.
  • Site configuration may disable live logs, direct execution, agent installation, structured result staging, or specific resource modes.

17 · Verification strategy

Test the transitions that ordinary integration tests miss

Test layers

  1. Pure unit and property tests: validation, normalization, codecs, state reducers, diagnostic combination, resource resolution, and schema reattachment.
  2. Golden protocol tests: real CLI JSON, parsable output, stderr, unknown fields, job states, reasons, arrays, accounting records, and agent frames across supported versions.
  3. Scheduler model: deterministic fake scheduler, command runner, transport, filesystem, clock, worker, and control store.
  4. Interpreter conformance: local CLI, SSH agent, and optional REST must satisfy the same laws.
  5. Container or disposable cluster tests: normal batch lifecycle, output files, accounting, cancellation, arrays, and version probes.
  6. Real-site acceptance: an unprivileged installation through the site's normal SSH path with recorded versions, capabilities, policy, and limitations.

Required fault scenarios

Core laws

  • Submission key + identical digest is idempotent.
  • Submission key + different digest conflicts.
  • Read-only retry never changes scheduler or workload meaning.
  • Stream finalization never cancels a remote job.
  • Event replay omits no committed event and tolerates duplicate delivery.
  • Log resume emits an exact byte continuation unless it explicitly reports a gap.
  • Backend binding and placement never change the result schema or operation identity.
  • Local and remote CLI interpreters normalize equivalent evidence equivalently.
  • Stale attempt epochs cannot provide an accepted structured result.

20 · Acceptance criteria

Definition of v1 success

  • The same opaque script can be submitted locally and through SSH without changing scheduler semantics.
  • Submission returns durable acceptance or an explicit rejected, unavailable, or acceptance-unknown outcome—not terminal completion.
  • A queued or running managed job outlives the caller fiber, local process, SSH connection, client, and restartable agent.
  • A lost submission response does not trigger blind automatic resubmission.
  • Temporary scheduler, accounting, filesystem, network, or parser unavailability does not invent workload failure.
  • Known and unknown Slurm states, reasons, flags, warnings, exit data, and raw bounded evidence remain accessible.
  • stdout and stderr resume from exact byte cursors, including after disconnect, with explicit gap or truncation reporting.
  • Failure diagnosis combines scheduler, accounting, worker, logs, and result evidence with confirmed/suspected/undetermined confidence.
  • An exit-zero opaque script with a missing declared output is not reported as a valid result.
  • A registered Scala task returns a schema-validated typed value; wrong-schema reattachment fails safely.
  • Typed tasks are deployed by operation identity and worker release; no closures or IO[A] values are serialized.
  • Cancellation is explicit, asynchronous, idempotent, and independent of local resource finalization.
  • Coalesced observation avoids one Slurm RPC loop per job and remains bounded under slow consumers.
  • Fake/model tests, disposable-cluster tests, and at least one real unprivileged Slurm site pass the required failure matrix.
  • Supported Scala, JDK, Slurm, data-parser, agent-protocol, and persistence-schema versions are documented.

Success measures

  • Every persisted state-machine edge has at least one deterministic crash or interruption test.
  • Every public interpreter passes a shared conformance law suite.
  • No unbounded queue, unbounded subprocess capture, or unbounded log line exists in the implementation.
  • Compatibility fixtures cover at least two supported Slurm major-release families before v1.
  • Real-site evidence records exact versions, capabilities, commands, configuration assumptions, and known limitations.

22 · Decisions and open questions

Current decisions

DecisionStatusRationale
Standard Slurm commands define the baseline interpreter.DecidedPortable, site-native authentication/configuration, sufficient functionality; robustness is above the transport.
Remote operation uses a fixed agent protocol over system OpenSSH.DecidedAvoids dynamic remote shell construction while respecting existing SSH policy.
FS2 is the live byte/event transport, not durable authority.DecidedBackpressure and resource safety without confusing in-memory delivery with persistence.
Raw and managed scheduler surfaces coexist.DecidedLow-level fidelity remains available while robust applications gain recovery and idempotency.
Opaque scripts and typed tasks share result contracts.DecidedLanguage does not determine observability; scripts may progressively adopt structure.
Arbitrary IO[A] and closures are not serialized.DecidedDeployment, code identity, effects, and retry behavior must remain explicit.
slurmrestd is optional after CLI parity.DecidedUseful for throughput and site integration but not universally deployed.
Native libslurm binding is excluded absent measured need.DecidedHigh platform and version cost with little initial semantic benefit.
Scala 3.3.8 LTS and JDK 17 define the v1 build baseline.DecidedA compiler reads TASTy from its own or an earlier minor line, so publishing from the LTS line keeps 3.3 consumers. 3.8.4 is a verification-only lane; publication-line changes require an explicit compatibility decision.

TermMeaning
